# Технический Аудит Проекта GameMind AI

## 1. Executive Summary
В ходе проведения глубокого технического аудита гибридного десктоп-приложения **GameMind AI** (Electron + React + SQLite + Supabase) был выявлен ряд критических уязвимостей в области безопасности, управления доступом и масштабируемости. Несмотря на то что фронтенд и локальная архитектура (SQLite кэширование, IPC-мост) спроектированы на приемлемом уровне, облачная инфраструктура (Supabase RLS) и интеграция с внешними AI API содержат фундаментальные архитектурные ошибки. Приложение в текущем виде **не готово к публичному релизу** (Production) из-за риска массовой утечки пользовательских данных, подделки сообщений и полного исчерпания лимитов API.

## 2. Общая Оценка
**Current Project Score: 3.5/10**

Проект имеет отличный UX и хорошую задумку гибридного хранения (Local-first + Cloud Sync), однако игнорирование правила "клиент не является доверенной средой" привело к тому, что все "приватные" фичи на самом деле полностью открыты на уровне API.

## 3. Критические Уязвимости и Баги (CRITICAL)

### CRITICAL: Полная утечка приватных данных профилей (RLS Bypass)
* **Файл:** `supabase/rls-policies.sql` (или соответствующая миграция)
* **Описание:** На таблицу `users` установлено правило `CREATE POLICY "Users can view any profile" ON users FOR SELECT USING (true);`. Это означает, что **любой** авторизованный (и даже анонимный, если включено) пользователь может сделать SELECT всей таблицы и выгрузить поля `dna_summary`, приватные списки друзей и скрытые бейджи. Клиентские настройки приватности (переменные `is_library_public`, `is_dna_public` и т.д.) применяются **только на UI**, скрывая элементы в React, но данные все равно передаются всем через API.

### CRITICAL: Подделка сообщений и спам (Chat Forgery)
* **Файлы:** `supabase/dm-migration.sql`, `supabase/chat-improvements.sql`
* **Описание:** 
  1. Политика `UPDATE` для сообщений позволяет получателю изменять строки, где он является `receiver_id`, без ограничений по колонкам (`WITH CHECK (auth.uid() = receiver_id)`). Это означает, что получатель может изменить `content` сообщения, присланного ему другим пользователем.
  2. Политика `INSERT` проверяет только `sender_id`. Любой пользователь может отправить сообщение любому другому, проигнорировав настройки `chat_privacy = 'friends_only'` и локальный Mute, и заспамить базу данных.

### CRITICAL: Вшитые API Ключи (Supply Chain / Financial Risk)
* **Файлы:** `src/main/services/ai/ai.client.ts`, `.env`
* **Описание:** Ключи `BUILTIN_GEMINI_KEY` и `BUILTIN_GROQ_KEY` хардкодятся в исходный код Electron (`app.asar`). Любой пользователь может распаковать приложение, извлечь ключи и использовать их для своих целей. Учитывая, что в будущем планируется переход на платные модели, это приведет к моментальным финансовым убыткам.

### CRITICAL: Неавторизованная выдача бейджей (Privilege Escalation)
* **Файл:** Таблица `user_badges` (Supabase) и `src/renderer/src/features/badges/hooks/useBadges.ts`
* **Описание:** Таблица `user_badges` в Supabase, судя по всему, не имеет строгих RLS ограничений на `INSERT/UPDATE`, так как фронтенд напрямую вызывает `.upsert()` для выдачи значков (`grantBadge`). Любой злоумышленник через DevTools или API-клиент может выдать себе значок `boss` (`badge_code: 'boss'`). Поскольку проверка на админа (Boss) на фронтенде (`UserProfilePage.tsx`) базируется на наличии этого значка, злоумышленник получит UI-права администратора.

## 4. Архитектурные Проблемы (HIGH / MEDIUM)

### HIGH: Фейковая (только клиентская) проверка прав Администратора
* **Файл:** `src/renderer/src/features/profile/UserProfilePage.tsx`
* **Описание:** Проверка `isBoss` (права на блокировку пользователей, выдачу бейджей) реализована исключительно на клиенте. Даже если злоумышленник не выдаст себе бейдж, он может перехватить логику React. При этом попытка вызвать блокировку (`handleBossBlockUser`) всё равно упадет с ошибкой на уровне БД из-за того, что RLS политики не позволяют менять статус дружбы на `blocked` кому угодно, кроме владельца. Отсутствует единый серверный (или RPC) слой проверки прав доступа (RBAC).

### HIGH: Уязвимости IPC обработчиков (Journal Admin)
* **Файл:** `src/main/ipc/handlers/journal.ipc.ts`
* **Описание:** Хендлеры `JOURNAL_ADMIN_GENERATE` и `JOURNAL_ADMIN_DELETE` вызывают сырой SQL-код (`DELETE FROM game_journals`) на локальной БД без проверки того, является ли пользователь настоящим админом. Хотя это влияет только на локальную БД, это ломает консистентность приложения.

### MEDIUM: Мусорный / Мертвый код в корне проекта
* **Файлы:** `test.py`, `test2.py`, `test_gemini.js`, `test_groq.js` и десятки других scratch-скриптов в корне.
* **Описание:** Проект содержит огромное количество скриптов для ручного тестирования, которые не удалены. Это засоряет репозиторий и может случайно попасть в релизные сборки, нарушая чистоту кодовой базы.

## 6. Тестирование при Масштабировании (Scalability Evaluation)

* **100 пользователей:** Система работает идеально. Лимиты бесплатных AI (Gemini/Groq) справляются с нагрузкой. Supabase Realtime (до 200 коннектов) держит онлайн-статусы.
* **1,000 пользователей:** Начинаются проблемы с AI. Вшитый `BUILTIN_GEMINI_KEY` начинает упираться в RPM (Requests Per Minute). У пользователей падают ошибки генерации ДНК и Журналов.
* **10,000 пользователей:** **Полный коллапс облака**. Supabase Free Tier блокирует подключения (лимит 500 коннектов даже на Pro для Realtime может быть превышен). Вшитые AI ключи уходят в бан за превышение лимитов или сжигают огромный бюджет, если привязана карта.
* **100,000 пользователей:** Steam API (200 запросов / 5 мин) может заблокировать IP-адреса серверов Supabase (хотя запросы идут с локальных машин клиентов, что спасает ситуацию, но только если каждый игрок не использует общий прокси). 

## 7. Приоритетный Roadmap

### Фаза 1: Немедленная безопасность (Security Patching)
1. **Переписать политики RLS на таблице `users`:** Возвращать приватные поля (`dna_summary`, и т.д.) только если `auth.uid() = id` ИЛИ `is_dna_public = true` ИЛИ они являются друзьями (зависит от настроек профиля).
2. **Переписать политики RLS на `messages`:**
   - Запретить `UPDATE` колонки `content` для `receiver_id`.
   - Внедрить проверку на `chat_privacy` прямо в `WITH CHECK` для `INSERT` политики (разрешать вставку только если пользователи друзья или у получателя открыты ЛС).
3. **Настроить RLS для `user_badges`:** Закрыть прямую вставку (INSERT) с фронтенда. Выдача бейджей должна происходить только через защищенную серверную функцию (Supabase Edge Function или Security Definer RPC).
4. **Удалить вшитые ключи AI:** AI-фичи должны либо использовать ключи пользователя (Bring Your Own Key), либо идти через ваш собственный промежуточный сервер (Backend), который скрывает ключи и биллит пользователей.

### Фаза 2: Рефакторинг Архитектуры
1. **Создать RBAC в Supabase:** Реализовать проверку ролей (Admin/User) через `custom claims` в JWT токене Supabase, а не через таблицу `user_badges`.
2. **Ограничить Realtime:** Подписываться на `supabase.channel` только при активном открытии чата, отписываться при закрытии, чтобы не исчерпать лимиты коннектов.

### Фаза 3: Чистота и Качество
1. Удалить все `test_*.js` и `*.py` файлы из корня.
2. Написать базовые unit-тесты (Vitest) для критических узлов: `json-utils.ts`, `recommendations-calculator.ts` и сервисов шифрования.
3. Унифицировать логгирование: заменить все `console.error` в сервисах на `logger.error`.
